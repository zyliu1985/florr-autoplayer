# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A full desktop automation bot for [florr.io](https://florr.io/) (a Canvas browser MMO). It drives a **fullscreen** florr.io tab in Chrome using real OS-level mouse/keyboard (pyautogui), reads the in-game minimap with OpenCV, runs YOLO enemy detection (ultralytics), injects JS into the game page over CDP, and wraps everything in a customtkinter control-panel GUI.

This is the source repo for the bot. A PyInstaller-packed build of it (and an older, minimal Playwright/extension sibling project with `main.py` + `extension/`) live **one directory up** (`D:\Codes\florr autoplayer\`) — that directory's CLAUDE.md describes *that* sibling, not this codebase. Don't confuse them.

**The one idea to internalize:** florr.io does not steer with WASD. The character walks toward wherever the real mouse cursor is, relative to the screen center. So "pressing W" = moving the mouse `delta` pixels above center, and "stopping" = returning the mouse to center. Everything downstream (see `utils.keydown`/`keyup`, `move_to_position`, the enemy-aim helpers) is built on this.

## Commands

```bash

# A working venv already exists at venv/ (created 2026-09-12); activate it first:
venv\Scripts\activate          # Windows — then python/pip below are the venv's

pip install -r requirements.txt   # heavy: torch<2.3, ultralytics, opencv-python<5, pyautogui, customtkinter, websocket-client, certifi, pyinstaller, pytest

python main.py                    # open the control-panel GUI (normal entry point)
python main.py --worker           # worker subprocess — spawned BY the GUI, don't run standalone

python -m pytest                  # unit tests (mock all external state: no real Chrome/screen needed)
python -m pytest test_cdp_bridge.py   # single file
```

- Known test-suite quirk: 10 tests in `test_overlay.py` are macOS-only (they assume pyobjc's `AppKit` is importable) and fail on Windows with `AttributeError: None has no attribute 'NSApplication'`. Ignore them; the Windows overlay path (`_WindowsOverlay`) is covered by the passing tests. `pytest.ini` exists only to keep pytest from recursing into `florr-auto-afk-v1.1.1-autostart/` (a runtime-generated third-party dir; `python -m pytest` from the repo root picks it up otherwise and chokes on torch's vendored tests).

- Most screens are needed for anything real: `python main.py --worker` errors out if the dedicated Chrome isn't ready (the GUI is what prepares Chrome + florr-auto-afk). Live-fire diagnostics live in `debug_*.py`, `map_select.py`/`area_select.py`, and `learn_shortcuts.py` (they need a real screen + game running; not unit-testable).
- No linter, no formatter, no CI, no git repo (plain folder).
- Code comments, README.md and PACKAGING.md are the docs; comments are written in Chinese — keep that register when adding to the code.

## Architecture

### Process model (GUI → worker)

- `python main.py` (no args) → `gui_app.py`. The GUI never runs bot logic. On 开始 it: validates inputs → ensures dedicated Chrome via `gui_chrome_flow.py` → (if AFK toggle on) ensures florr-auto-afk → asks user to F11 fullscreen → writes `config.json` → `subprocess.Popen(["python", "main.py", "-u", "--worker"])` and streams the child's stdout into its log box.
- **Stop = close the worker's stdin pipe.** The worker runs `_install_worker_stdin_watcher()` (a thread doing `sys.stdin.read()`), which on EOF calls `reset_keyboard()` (releases any held space/WASD — otherwise they stay stuck down in-game) then exits. This is load-bearing: in the packaged `console=False` exe, SIGTERM/SIGBREAK don't reliably arrive; stdin EOF is the only cross-platform stop signal. The GUI also force-kills after 3 s if the worker won't die.
- Worker loop (`run_worker`): on death/menu screens it clicks the continue/start buttons and starts a new round automatically. It never launches Chrome or florr-auto-afk itself (see "Trip-ups").

### The two coordinate spaces (never mix them)

1. **Minimap space** — a fixed 300×300 grid, same as `maps/{desert,ocean,anthell,garden}.png`. Used for pathfinding (`lazy_theta_star`), player position, farming areas. `map_select.py`/`area_select.py`/`gui_map_picker.py` produce coordinates in this space.
2. **Screen space** — physical pixels. All UI constants were measured at 1920×1080 and are scaled at runtime by `scale_x`/`scale_y`/`mouse_scale()` in `utils.py`. `get_player_position()` and pathing produce minimap coords; `enemy_detect`'s aim/flee helpers and `move_to_position`'s cursor math produce screen coords.

### Core loop pieces

- **Screen-state detection:** `on_death_screen()` / `on_start_screen()` sample a small region around the green "继续"/"开始" button for the fraction of green pixels. **Do not "fix" these back to `check_stage()`** — that single-pixel signature path is legacy and has never reliably triggered on a real machine.
- **Teleport recovery (传送门逃生):** respawning in anthell can drop the bot onto a portal, teleporting it to **garden**. `is_on_garden()` (utils) detects this by NCC-matching the captured top-right minimap against `maps/garden.png` (also a legit farmable map — it's in `app_config._VALID_MAPS`). `recover_from_teleport()` (main) then temporarily `apply_map("garden")`, pathfinds to the fixed `GARDEN_PORTAL_COORD`, walks into the portal (waits out the black-screen transition via `screen_is_black()`), and restores the original map. The `_teleport_recovery_active` flag prevents recursion (the recovery's own `lazy_theta_pathing` loop-top garden check must not re-trigger). **Crucially, every "on garden" check in the loops is gated by `_garden_escape_needed()` (main) — which returns False when the farming target itself is garden** (otherwise a garden farming session would read `is_on_garden()` True forever and constantly try to escape). Checked in `move_to_position` every `TELEPORT_CHECK_EVERY` ticks and at the tops of the `lazy_theta_pathing` / `auto_farming` / `run_worker` loops. Missing `maps/garden.png` degrades to no-op (no crash).
- **Player position:** `get_player_position()` color-matches the player marker (`f8de60`) in the captured minimap, then `calibrate_player()` snaps to the nearest walkable pixel. It can return a *fake* position on death/menu screens (a stray pixel matching the marker color) — that's why every loop checks death/menu *before* trusting the position.
- **Minimap capture:** `get_map()` crops the minimap widget using a **uniform** scale by `SCREEN_HEIGHT/1080` anchored top-right (not per-axis stretch — verified on a real 1024×768 machine, see the resolution design doc), then `cv2.resize`s back to 300×300. Changing this breaks position detection at non-1920×1080 resolutions.
- **Pathfinding:** A\* with wall-keepout cost lives in `main.py` (`find_walkable_path` → `find_path` + `_bfs_dist_to_wall` + `_smooth_path`), ported from the sibling `my-auto-pathing-system/pathfinder.py`. Cells within `WALL_KEEPOUT` of a wall get an elevated cost (so paths prefer wide corridors but still squeeze narrow ones — the erosion alternative disconnects anthell), diagonal moves require both orthogonal neighbors passable (no corner-cutting — the old Lazy Theta\* jammed in narrow corridors by threading 1-cell diagonal gaps), endpoints snap to the nearest passable cell (`_snap_to_passable`, also fixes goals clicked on walls), and `_smooth_path` string-pulls the dense A\* path via corner-safe LOS (stays per-pixel in narrow corridors, straight lines in open areas). `lazy_theta_pathing()` re-plans forever until arrival/death/menu — "stuck" triggers `_run_escape()` and retries. `_run_escape` (main.py) BFS-finds the nearest wall (`_nearest_wall_direction`) and pushes directly away from it for `ESCAPE_HOLD_SECONDS` — the direction is computed **once**, deliberately: re-steering every step flips the direction back and forth in narrow corridors and never breaks the jam, and target-direction is *not* blended in. `execute_anti_stuck` (utils.py) is the wall-color/random fallback when position/map are unavailable or no wall is within range. `move_to_position` treats a waypoint as reached within `ARRIVE_RADIUS` (2px) — larger values make the bot cut corridor corners and jam.
- **Farming:** `auto_farming()` wanders continuously inside the farming area (rejection-sampled walkable points), never pausing to stand still. Its `move_to_position(..., on_tick=...)` hook lets a wander leg be interrupted mid-step when the enemy scan wants to flee/chase — `move_to_position` is otherwise a blocking ~10 s call. **Two modes, switched by the `farming_path` kwarg** (config `farming_path`, default `None`): area mode = random wander inside `farming_area` (legacy); **fixed-path mode** = walk the user-drawn path points in order via `move_to_position`, loop back to the first point after the last (not a return-trace — user chose "循环"), never advancing the index on a stuck/escape so the jammed point gets retried, and skips the "left farming area → re-path" check (a path has no single-area semantics). `run_worker` passes the path to `auto_farming` and uses `[]` as the arrival area for `lazy_theta_pathing` (path start = target point, no box to arrive into). GUI (`gui_map_picker.py` + `gui_app.py` mode segmented button) draws the path as an orange polyline (green start / red end), left-click appends a point (first point doubles as the target point), right-click undoes the last point.
- **Enemy AI (`enemy_detect.py`)** — off by default, desert map only, needs `models/desert.pt`:
  - YOLO detects 6 species; rarity is read by sampling the colored name text *below* each monster's green HP bar (the HP bar is the anchor). Bars thinner than ~4 px read as Common — so before farming, `ensure_zoom_for_rarity()` scrolls the camera (via CDP wheel events) until HP bars are thick enough.
  - `select_action()` → `("flee", …)` / `("chase", target, hold_px, repel)` / `("wander", None)`. Chase is deliberately reserved for Mythic+ (and Ultra CAUTIOUS) — chasing every high-score common sandstorm made the bot micro-vibrate in place.
  - Mythic proximity latch (`pick_mythic_target` + `MYTHIC_*` constants in `main.py`): locks onto a close Mythic and kites it per-species (ram/hold/strafe), with hysteresis on release.
  - A dedicated `scan_bar_thickness()` avoids the per-box rarity cost when only judging zoom.

### Integration modules

- **`cdp_bridge.py`** — minimal CDP client over WebSocket (`eval_js`, `capture_screenshot`, `scroll_wheel`) + the Chrome bootstrap. Requires Chrome launched with exactly three flags: `--remote-debugging-port=9222 --remote-allow-origins=* --user-data-dir=<independent profile>` (any one missing = silent failure; documented at length in the module docstring). Also `quit_and_launch_chrome()` (taskkill all Chrome + relaunch with flags) and `is_dedicated_chrome_ready()`.
- **`server_lookup.py` + `utils.switch_server()`** — on repeated "short rounds" (bot keeps dying before farming the full duration), queries florr.io's *official* M28 server API (live IDs — no stale manual list), picks one unused in the last 30 min, and runs `cp6.forceServerID("…")` inside the page via CDP.
- **`afk_watch.py`** — coexists with the external **florr-auto-afk** program (a third-party AFK-popup solver, auto-downloaded as `florr-auto-afk-v1.1.1-autostart/segment.exe` with a pinned SHA-256). The bot polls its `latest.log` for `"EVENT: Found AFK window"` and pauses the main loops for `PAUSE_SECONDS` so the two don't fight over the mouse. The GUI owns segment.exe's lifecycle; the worker only `poll_afk_pause()`s.
- **`overlay.py`** — click-through, always-on-top status HUD: macOS uses AppKit/PyObjC (must span Spaces over the fullscreen game), Windows uses tkinter + raw win32 extended styles. `create_overlay()` degrades to a `_NullOverlay` rather than crash. Its confirm-dialog `show_fullscreen_confirm()` similarly falls back to console `input()`.
- **`app_config.py`** — `config.json` next to the executable; GUI writes, worker reads. `DEFAULTS` are the pre-refactor hardcoded values; every key is coerced per-key and unknown/broken values fall back to defaults.

### Packaging (`PACKAGING.md`, `main.spec`, `build_windows.bat`)

PyInstaller one-dir build (torch makes it ~1 GB), `console=False`. Maps/models are **not** bundled via `--add-data`: the code opens `./maps/...` and `models/desert.pt` relative to cwd (the exe's own folder), so `build_windows.bat` copies `maps\` next to the exe and `models\desert.pt` must be copied in by hand. Build only on Windows (PyInstaller doesn't cross-compile).

## Things future-me will trip on

- **`models/desert.pt` is not committed** (gitignored, third-party YOLO weights — this working tree has it, plus `models/sandstorm.pt`). The bot auto-disables enemy AI on non-desert maps or when the file is missing. `sandstorm.pt` is only used by `debug_enemy_detect.py` to sanity-check desert.pt's class-3 'sandstorm' boxes side by side; the bot itself loads only desert.pt. `.pt` is pickle-based and can execute code on load — only use a model from a source you verified; never wire in a script that downloads arbitrary `.pt` without a human confirming.
- **`websocket` vs `websocket-client`:** two unrelated PyPI packages both import as `websocket`. `cdp_bridge` installs a runtime check with clear remediation (`pip uninstall websocket websocket-client && pip install websocket-client`). Install failures with `no attribute 'create_connection'` point here.
- **certifi is load-bearing on Windows** — Python's urllib/ssl won't read the OS cert store there; `server_lookup.py` and `afk_watch.py` build explicit SSLContexts from certifi.
- **DPI awareness:** `utils.py` calls `SetProcessDpiAwareness(1)` on Windows so `pyautogui.size()` and coordinates are real physical pixels. Don't remove it.
- **Don't teach the worker to start Chrome or florr-auto-afk.** `run_worker` deliberately only verifies `is_dedicated_chrome_ready()` and exits with a message otherwise; in a `console=False` exe the worker's stdin is dead, so `input()` prompts crash it. The GUI owns all interactive setup.
- **Comments are Chinese; keep them that way.** English is fine for new standalone docs but match the file you're in.
- **Reserved constants to keep in sync:** map names appear in `maps/` filenames, `utils.apply_map()`'s assert, `utils.MAP_WALL_COLORS` (anti-stuck wall color — maps without an entry degrade to random-direction anti-stuck instead of crashing), `utils.PLAYER_MARKER_COLORS` (player-marker color per map — **not the same on every map**; garden is `dddd63`, anthell is `f8de60`; getting this wrong makes `get_player_position` return None and nothing navigates), `utils._SERVER_SWITCH_BLOCKED_MAPS` (maps where auto server-switching is disabled — ant_hell crashes the game), `app_config._VALID_MAPS`, `app_config.DEFAULTS["farming_path"]` (fixed-path mode config key — must stay `None` by default so legacy configs keep using area mode), `server_lookup.MAP_TO_BIOME` (map name → server-API biome name; only anthell differs — `anthell` vs `ant_hell`), and `enemy_detect`'s desert-only model gating. Add a map = update the ones that apply.
- **`debug_*.py` scripts** are live-fire diagnostics (screenshot/color forensics, screen-coordinate marking) — they print suggested fixes but need a real display + game. The `debug_*.png` images in the root are their outputs; `compare.jpg` is the README's lazy-theta\*-vs-a\* illustration (keep it). Root-level `ocean_wall.png` is the user screenshot that backs `utils.MAP_WALL_COLORS["ocean"]` (RGB 156,115,153) — provenance only, distinct from `maps/ocean.png`. Root-level `garden.png` is a captured minimap screenshot, **not** the `maps/garden.png` template the teleport-recovery NCC matcher loads — don't confuse the two. (`maps/garden.png` is now also a normal farmable map, not just a teleport template — see the "Teleport recovery" bullet above.)
- **`learn_shortcuts.py` edits `maps/<地图名>.png` in place — any map, default `anthell`** (`python learn_shortcuts.py desert` etc.). Maps have hidden shortcuts that aren't drawn on the minimap template, so a player walking through one reads as "inside a wall". This live-fire tool (game must be running on that map, fullscreen) polls the *raw* player marker, detects in-wall positions, and carves the traversed wall segments into the map's PNG (a Bresenham line between consecutive samples, radius `CARVE_RADIUS`), saving after each step. The committed `anthell.png` has already been carved this way — don't replace it with a vanilla anthell PNG or those shortcuts vanish for the pathfinder. It uses the raw position, not `get_player_position()` (which snaps to the nearest walkable cell and can never report "in wall"). Map selection relies on `utils.PLAYER_MARKER_COLORS[map]` already being configured — add a new map to that dict first or the marker won't be found.
- **`florr-auto-afk-v1.1.1-autostart.zip` (~1.2 GB) sits in the repo root and is not gitignored.** It's the packaged third-party AFK tool; the runtime copy is the auto-downloaded `florr-auto-afk-v1.1.1-autostart/` dir (which *is* gitignored). Don't unzip it over the source dir, and add it to `.gitignore` before any `git init`.
- Design/plan docs live in `docs/superpowers/{specs,plans}/2026-*.md` (resolution adaptation, Chrome bootstrap, enemy detection, AFK coexistence, zoom gating, …). They explain *why* the code is shaped the way it is — read the relevant one before refactoring an area.
